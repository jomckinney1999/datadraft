# SQL Sports

Education platform teaching SQL and data analytics through fantasy football. Next.js 14 (App Router), TypeScript, Tailwind — a marketing/landing site (`app/page.tsx`) plus a gamified learning MVP (`app/learn/`), deployed to Vercel at https://sql-sports.vercel.app.

## Design system

Fantasy-football palette, defined once in `tailwind.config.ts` + `app/globals.css`: `night` (draft-night indigo #0C1022 family), `turf` (green #3FD973, primary accent), `gold` (championship gold #F2C94C, secondary), plus `ink`/`panel` neutrals. These replaced an older teal/amber scheme in Aug 2026 — never reintroduce `teal`/`amber` token names, and change colors by editing token values, not component classes.

### Light + dark mode

Both themes ship. Every token resolves through a CSS variable holding an `"r g b"` channel triplet — declared in `app/globals.css` under `:root` (dark, the default) and `:root[data-theme="light"]`, wired into Tailwind as `rgb(var(--c-x) / <alpha-value>)`. That indirection is what keeps the ~186 alpha modifiers (`bg-turf/10`, `border-panel-border/60`) working while the palette flips.

- **Use the tokens.** Never hardcode a hex, `rgba()`, or `text-[#...]` in a component — it won't flip. For glows/scrims/gradients that need per-theme tuning, add a class in `globals.css` (see `.rays-turf`, `.yard-lines`, `.edge-glow-gold`) rather than an inline `style`. Coach Blitz (`components/coach.tsx`) is the deliberate exception — it's an illustration, and its hexes stay fixed in both themes.
- **Light-mode turf and gold are far darker** than their dark-mode values, calibrated against the tightest real pairing (accent text on an accent/10 chip), not against plain white. Every token pair clears WCAG AA 4.5:1 in both themes — re-measure if you change them.
- `--glow-strength` is `1` in dark and `0` in light, so the scoreboard glow classes multiply to nothing on white instead of smearing.
- `.theme-dark` re-asserts the dark values on any subtree, if a section ever needs to stay dark in light mode.
- **The toggle lives in every route's header** (`components/theme-toggle.tsx`), except the lesson player — its top bar is deliberately minimal (quit / progress / hearts). Choice persists in `localStorage` under `sqlsports-theme` and defaults to the OS preference until the visitor picks explicitly.
- `app/layout.tsx` runs a blocking inline script that sets `data-theme` before first paint. It mirrors the resolution order in `theme-toggle.tsx` — **change both or neither**, or the page flashes the wrong theme on load.
- **Don't remove the `.theme-switching` transition suppression.** Chrome does not re-resolve a `var()`-derived color on an element with an active `transition-colors`, so without it every button, card, and nav link stays painted in the *previous* theme's colors after a toggle. It is a correctness fix, not polish.

## Sport selection

The learner picks football, basketball, or baseball as their lens (`lib/sports.ts`, `components/sport-picker.tsx`, persisted via `lib/use-sport.ts` under `sqlsports-sport`). Football is `status: "live"` — it's the only one with a real dataset (`public/field-data.json`); basketball and baseball are `status: "building"` and are labeled that way everywhere they appear. Don't mark a sport live until a pipeline actually backs it. The choice is kept in its own localStorage key rather than in `lib/progress.ts` to avoid touching the progress schema — fold it into `Progress` when accounts land (LAUNCH-PLAN Phase 1).

## Gamified learning MVP (`/learn`)

Duolingo-style lesson player + DataCamp-style course roadmap, fully client-side (no accounts, no backend):

- **Catalog:** `/learn` is a card grid of all nine courses (`lib/courses.ts`); clicking one opens `/learn/track/[moduleId]`, which renders `components/course-roadmap.tsx`. The static `track` segment sits above the lesson player's `[lessonId]`, so the two don't collide. Courses with no lessons yet have `moduleId: null` and render as non-clickable "In build" cards — don't make one clickable before its lessons exist. Full lesson-by-lesson plans for all nine courses are in [docs/COURSE-CATALOG.md](docs/COURSE-CATALOG.md).
- **Content:** `lib/curriculum.ts` — 17 live units / 59 lessons / 271 exercises (mc, tap-the-word fill, write-real-SQL `query`, live `code` for Python/R, live `formula` for Excel). `u1`–`u6` are the complete SQL course; `u7`+`u13`+`u14` are the Python course (foundations → logic/functions → pandas for real data); `u8`–`u11` are statistics, visualization, Git/GitHub and R; `u15`–`u18` are the Excel course (grid/first formulas → logic → lookups → cleaning).
- **Unit ids are not display order.** `MODULES[].unitIds` defines both which units a course contains AND the order they appear in — `moduleUnits()` sorts by that list, not by position in `COURSE.units`, so units added later (Python's `u13`/`u14`) still sit beside `u7`. The roadmap numbers units by position within the selected module, so a course always reads Unit 1, 2, 3 regardless of its ids. Learners pick a course from the `/learn` catalog; the choice is stored via `lib/use-module.ts` so the lesson player advances within that course.
- **Live coding:** `query` exercises execute against sql.js (SQL only). `code` exercises run Python (Pyodide), R (WebR), or SQL via `lib/runtimes.ts` and grade printed output. `formula` exercises evaluate real Excel formulas against the workbook in `lib/excel-data.ts` (see below). Stats/viz/Git stay on `mc`/`fill` (no REPL). **Don't add a `query` exercise to units 7–11** — use `code` with `lang: "python" | "r"` when the learner should run real code, and **`formula` (never `query` or `code`) in the Excel units 15–18**.
- **Editors are `components/code-editor.tsx`** — every code surface (both lesson-player editors, the landing sandbox, the Practice Field) goes through it. It's a real `<textarea>` with a highlighted `<pre>` behind it and transparent text on top, so selection, undo, IME, mobile keyboards and screen readers all keep working; no CodeMirror/Monaco. Tokenizing lives in `lib/highlight.ts` (regex, not a parser — it only has to be stable per keystroke, and it returns token objects rather than HTML so learner input can never become markup). **The two layers must lay out glyphs identically or the caret drifts off the text** — shared geometry is in the `.code-layer` class and the padding/size classes are passed to both; change one, change the other. Syntax colours are `--c-syn-*` tokens in `globals.css` with a light-mode set, and all six clear AA in both themes.
- **Grading:** query exercises run learner SQL and the `expected` answer key against the same in-browser sql.js database (seeded from `lib/fantasy-data.ts`) and compare result values; `orderMatters: false` sorts rows first.
- **Excel runs for real** — `lib/excel-engine.ts` evaluates learner formulas against the two-sheet workbook in `lib/excel-data.ts` (`Roster` clean, `Import` deliberately dirty) and grades on the **value produced**, not the formula text, so any correct spelling passes. Three things to know before touching it:
  - **The engine is `fast-formula-parser` (MIT) and the licence is the reason.** HyperFormula is more complete but **GPL-3.0-only**, which would force this whole app to GPL — never swap it in. The tradeoff is a partial function library, so `MAX`, `MIN`, `COUNTA`, `COUNTBLANK`, `MEDIAN`, `LARGE`, `SMALL`, `SUMIFS`, `COUNTIFS`, `AVERAGEIFS`, `MATCH`, `XLOOKUP`, `UPPER`, `LOWER`, `PROPER`, `TEXTJOIN`, `SUBSTITUTE` and `VALUE` are implemented in `customFunctions()`. Check a function actually evaluates before writing a lesson around it.
  - **A formula that references no cell is rejected even when its value is right** (`referencesCells()`), or a learner could read 402.5 off the grid and type `=402.5`. Set `allowLiteral: true` only if a drill genuinely has no cell to point at.
  - **`components/excel-grid.tsx` is read-only by design.** Building an editable fake Excel would teach habits that don't transfer; the learner reads real addresses off the grid and types real formulas against them.
- **Run `node scripts/verify-answer-keys.mjs` after touching any `query`, Python `code`, or Excel `formula` exercise, or any `previewSql` / `previewSheet`.** Excel keys are evaluated by the shipped engine (loaded through `scripts/load-ts.mjs`, which transpiles project TS for Node) and fail on a key that errors, returns blank, names a missing sheet, or hardcodes its answer — that last one would mean the exercise's own anti-hardcode guard rejects the model answer. It also executes every Python answer key in Pyodide (same runtime as the browser) and fails if one errors or prints nothing — grading compares printed output, so a silent key marks every learner wrong. R keys are skipped (no supported Node build of WebR) and the script says so rather than passing them silently. It executes every answer key and brief preview against the real seeded database and fails on three things: a key that errors, a key returning zero rows, and a LIMIT whose cutoff is tied on *every* ORDER BY column (which lets a correct learner query grade wrong — add a tie-break to the prompt and the key). It already caught a brief previewing `fantasy_pts > 30` back when the dataset was synthetic and capped at 28.9.
- **The lesson data is REAL, and that is load-bearing.** `week_results` is nflverse-data weekly PPR fantasy points, 2022–2024 regular seasons, one row per game actually played — 876 rows, 20 players, weeks 1–18, points from −0.1 to 55.4. It is baked into `lib/lesson-data.generated.ts` by `scripts/build-lesson-dataset.mjs` (re-run to refresh or add seasons; it also rewrites the learner CSVs in `public/data/`). Things to keep true:
  - **Never go back to generated data.** The previous synthetic generator produced impossible history — Tyreek Hill on Miami in 2016, Puka Nacua playing before he was drafted — and a learner spotted it. `SELECT * FROM week_results LIMIT 5` also showed the same player five times, because rows were emitted player-major. The generated file is ordered season → week → points desc precisely so the first table anyone sees is five different players.
  - **`rosters` and `waiver_wire` are invented** and must stay labelled that way. Who owns a player is a fact about one private league, not the NFL. `PROVENANCE` in `lib/data-source.ts` marks each table `real` or `league`, and `/data` renders it.
  - **Attribution is required** (CC BY 4.0). `SHORT_CREDIT` from `lib/data-source.ts` appears on every lesson brief and in the sandbox schema panel, and `/data` carries the full citation plus free downloads. Don't remove them.
  - **Real data has gaps.** Missed games are absent, not zero — which is why `COUNT(*)` on McCaffrey returns 37 rather than 50, and why the LEFT JOIN lesson has two genuinely missing players. Lesson prose that quotes a number is checked against the database, not assumed; re-run the audit after any dataset rebuild.
- **Progress:** localStorage only (`lib/progress.ts`, key `sqlsports.progress.v1`) — XP, daily streak, completed lessons. Swaps for the Supabase `progress` table when accounts land (LAUNCH-PLAN Phase 1).
- **Beta bench (`/demo`):** internal QA surface, deliberately **not linked from the site nav**. Arms a demo profile in one click (fills the `username` / `draftedTrack` / `playbookStyle` the lesson player gates on), flips playbook style to compare how one lesson renders in each mode, and links straight into every lesson with its exercise-type counts. It reads and writes the same localStorage progress the real player uses, so what you test is the real thing — keep it that way rather than giving it a mock mode.
- **Mascot:** Coach Blitz, `components/coach.tsx` — inline SVG with a `mood` prop; no image assets.
- **Draft Day:** `app/learn/draft/` is the course-selection ceremony — username ("name on the jersey"), a draft board of tracks from `lib/draft.ts` (one live, three "declaring next season"), and the commissioner announcement ("With the first pick of the SQLSports Draft, {username} selects …"). Stored as `username`/`draftedTrack` in progress. Onboarding gate order in the lesson player: draft → playbook quiz → lessons.
- **Every lesson opens with a `brief`** (`LessonBrief` in `lib/curriculum.ts`): `goal`, `setup`, and for SQL lessons a `previewSql` that runs live against the seeded database so the learner *sees the actual rows* before being asked anything about them. **All three playbook styles get the brief, Gunslingers included** — they previously landed cold on questions like "one row in week_results represents…" having never been shown a row. Adding a lesson without a brief is a regression; the field is required by the type.
- **Playbook styles:** `lib/playbook.ts` defines three learning modes (Film Room General / Gunslinger / Dual-Threat) + the onboarding quiz at `app/learn/playbook/`. The lesson player redirects to the quiz until a style is stored in progress. Tailoring hooks in `lib/curriculum.ts`: `film` cards on a lesson = bonus theory shown only to Film Room; `drillSkip: true` on an mc exercise = removed for Gunslingers (only tag pure-recall checks, never gotcha questions). Gunslingers skip the theory cards after the brief, get hints behind a toggle, and on any lesson with ≥3 hands-on exercises (`query`/`code`/`fill`) they skip **all** multiple choice for a typing-only run — the floor exists so concept-only units (stats, viz, git) aren't emptied out.
- **XP is echoed in the learner's sport** — "+10 XP · 10 yards" for football, points/bases for basketball/baseball, driven by `lib/use-sport.ts`.
- **Practice Field (`/field`):** ungraded free-play sandbox over real NFL data. `scripts/build-field-dataset.mjs` downloads nflverse `stats_player` weekly CSVs (note: the *new* release tag — the older `player_stats` tag used by `lib/data/nflverse.ts` stops at 2024) and bakes `public/field-data.json` (~300 KB: latest-season weekly + 3-season summaries + 32 teams). Re-run it each season with `WEEKLY_SEASON` bumped. `lib/field-data.ts` holds the schema/seed builder and the drill-book prompts; UI in `components/field-sandbox.tsx`.
- `middleware.ts` deliberately no-ops when `NEXT_PUBLIC_SUPABASE_URL` isn't a real http(s) URL (placeholder env values) — same lazy-init contract as `lib/stripe.ts`. Don't revert; with placeholder keys the Supabase client throws in middleware and takes down every route locally.


## Beta readiness (added 2026-08-28)

- **Nothing is for sale.** All pricing CTAs either go to `/learn` (free tier) or capture email via `components/waitlist-form.tsx`. Wiring Stripe checkout is blocked on real prerequisites, not effort: `docs/legal/` is still DRAFT, `docs/BUSINESS-SETUP.md` has no DBA/EIN/bank account, and `STRIPE_WEBHOOK_SECRET` is empty so subscription status could never sync back. Don't add a checkout button before those land.
- **Email capture** — `POST /api/waitlist` → `public.waitlist` (migration 0003). Rows carry `interest`, `sport` and `source` so the list is segmented from day one. RLS allows INSERT only: **there is deliberately no SELECT policy**, so the anon key can't read the list back. Read it from the dashboard or with the service role.
- **Accounts** — magic link only, at `/account`, with `/auth/callback` exchanging the code. Accounts are **optional**: everything works signed out, and progress stays in localStorage until someone signs in. `lib/progress-sync.ts` merges local and remote by **unioning completed lessons and taking max of counters** — last-write-wins would delete work when a learner switches devices. Progress lives in `public.learner_progress` (migration 0004), which mirrors the `Progress` type 1:1; the older `lesson_completions` table from 0001 is shaped for the retired 12-week syllabus and is unused.
- **`middleware.ts` skips anonymous visitors** (no `sb-*-auth-token` cookie → return immediately) and races `getUser()` against a 2.5s timeout. Both matter: it otherwise made a blocking network call on every page view for visitors with no session, and a slow auth server would hang the whole site instead of degrading to signed-out.
- **The draft board is derived from `lib/courses.ts`**, not hand-written — it drifted badly once the nine-course catalog shipped. `normalizeTrackId()` maps pre-catalog track ids forward so existing learners don't see a broken pick.
- **Basketball and baseball are not selectable.** Every lesson, the sandbox and the Practice Field are NFL data (327 football references in `lib/curriculum.ts`, zero for the other two). The picker labels them and offers a waitlist instead of a choice that changes nothing.

## Deployment

## Backend (Phase 0/1/2/3 of LAUNCH-PLAN.md — scaffolded, not yet live)

- **Stack:** Supabase (Postgres + auth) + Stripe (payments), decided in `docs/LAUNCH-PLAN.md` Phase 0. Client helpers in `lib/supabase/` (`client.ts` browser, `server.ts` server components/route handlers, `admin.ts` service-role for webhooks/cron — bypasses RLS, server-only). `middleware.ts` refreshes auth sessions on every request; required by `@supabase/ssr`, don't remove it.
- **Schema:** `supabase/migrations/*.sql`, run manually via the Supabase Dashboard SQL Editor (no CLI dependency yet). `0001_init.sql` — profiles/subscriptions/progress/challenges/leaderboard/fantasy-links/capstones. `0002_player_stats.sql` — real NFL stats table.
- **Payments:** `lib/stripe.ts` exports a lazy `getStripe()` singleton — **never instantiate the Stripe client at module top level**, it crashes the build (and would crash Vercel's build too) whenever `STRIPE_SECRET_KEY` isn't set. Checkout in `app/api/checkout/route.ts`, webhook in `app/api/stripe/webhook/route.ts`. `scripts/setup-stripe-products.mjs` creates the Practice product/price once a real key exists.
- **Data pipeline:** `lib/data/nflverse.ts` fetches real weekly NFL stats from nflverse-data's `player_stats` GitHub release (verified live before writing — see git history for the research). `lib/data/sleeper.ts` wraps Sleeper's public API (no auth needed, foundational for Phase 5 fantasy-platform sync). `app/api/cron/ingest-stats/route.ts` is the scheduled ETL job wired to Vercel Cron via `vercel.json`; protected by `CRON_SECRET`.
- **Env vars:** see `.env.local.example` for the full list required (Supabase URL/anon/service-role keys, Stripe secret/webhook/price keys, `CRON_SECRET`). None of this works until real values are added to `.env.local` (local) and the Vercel project's environment variables (production) — the build succeeds either way by design (everything's lazily initialized), but the routes themselves will error at runtime without real keys.
- **Legal:** draft Terms of Service / Privacy Policy / Refund Policy in `docs/legal/` — explicitly marked DRAFT, need real review before Phase 2 (real payments) goes live. `docs/BUSINESS-SETUP.md` is the entity/banking/tax checklist — guidance only, not something to execute autonomously.
